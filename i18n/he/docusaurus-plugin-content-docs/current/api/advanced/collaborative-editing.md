# עריכה שיתופית

המתודה `getSharedStore()` הופכת עורך לצומת בסשן עריכה שיתופית.  
היא משגרת כל שינוי כזרם פעולות ומחילה את הפעולות שעורכים אחרים שולחים בחזרה – יש לספק את שכבת התעבורה ביניהם (WebSocket, WebRTC או כל דבר אחר שיכול לשאת JSON).  
זוהי אחת המתודות של [ErdEditorElement](../erd-editor-element.md), והיא משמשת יחד עם [אחסון מרוחק](./remote-storage.md) כאשר יש גם לאחסן את השינויים שמועברים הלאה.

```ts
interface ErdEditorElement extends HTMLElement {
  // ...
  getSharedStore: (
    config?: SharedStoreConfig & {
      mouseTracker?: boolean;
      focusTracker?: boolean;
    }
  ) => SharedStore;
}

type SharedStoreConfig = {
  getNickname?: () => string;
};

type SharedStore = {
  connection: () => void;
  disconnect: () => void;
  dispatch: (actions: Array<AnyAction> | AnyAction) => void;
  dispatchSync: (actions: Array<AnyAction> | AnyAction) => void;
  subscribe: (fn: (value: AnyAction[]) => void) => Unsubscribe;
  flushStreamBuffers: () => void;
  destroy: () => void;
};

// example
const sharedStore = editor.getSharedStore();
```

פעולה היא אובייקט פשוט שניתן לבצע עליו סריאליזציה ושמתאר שינוי אחד במסמך, ולכן היא עוברת את `JSON.stringify` בשלמותה בדרכה לשכבת התעבורה.  
הפעולות מגיעות באצוות: המתודה `subscribe` מוסרת מערך, והמערך הזה הוא יחידה אחת – יש להעביר אותו הלאה בשלמותו ולהחיל אותו ב-`dispatch` בשלמותו בצד השני.  
יש להתייחס לפעולה כאל אובייקט אטום ולהעביר אותה כמות שהיא, בלי לקרוא או לשכתב אותה, כי המידע הפנימי שהיא נושאת הוא ששומר על העורכים מסונכרנים.

חלק ממה שעורך עושה נשאר באותו עורך.  
העברת טבלה, פתק או קבוצת טבלאות לחזית, כפי שקורה כשבוחרים באחד מהם, אינה נשלחת.  
גם הבחירות `Statements`, `Header`, `Write logical names into empty comments` (החל מגרסה `4.2.0`) ו-`Tables` בכרטיסיית [סכמת SQL](../../guide/guides/schema-sql.md), השייכות לחלון שבו הן נעשות, אינן נשלחות.  
החל מגרסה `4.1.0`, גם ה[סייר](../../guide/guides/explorer.md) נשאר בעורך שלו: האם הוא פתוח, הרוחב שלו, השורות המכווצות בו, השורה שעליה נמצא פוקוס המקלדת, מיקום הגלילה של העץ שלו, והחיפוש והאפשרויות שלו אינם נשלחים.  
גם ה[הארה](../../guide/guides/relationship-editing.md#reading-a-connector) שמעבר אל מפתח זר מוסיף לקו של הקשר שלו אינה נשלחת.  
החל מגרסה `4.2.0`, גם כרטיסיית [מילון](../../guide/guides/dictionary.md) נשארת בעורך שלה: איזה גיליון מוצג, והחיפוש, הבחירה, הגלילה ורוחבי העמודות של כל גיליון אינם נשלחים. העריכות, המיונים וייבואי ה-CSV בה כן נשלחים.  
גלילה, זום או החלפת כרטיסייה נשלחים, אבל לעולם אינם מזיזים את התצוגה או את הכרטיסייה של משתמש אחר. הדבר כולל את הגלילה שמבצעת קפיצה מהסייר, את המעבר לכרטיסיית ERD כשהסייר נפתח מכרטיסייה אחרת, ואת החלפת הכרטיסייה והגלילה של קפיצה מהגיליון [`Checks`](../../guide/guides/dictionary.md#the-checks-sheet) של כרטיסיית מילון לטבלה או לעמודה. קפיצה מהגיליון הזה למילה, למונח או לתחום נשארת בכרטיסיית מילון, ולכן שום חלק ממנה אינו נשלח.

החל מגרסה `4.2.0`, גם החלפה של [תצוגת השמות](../../guide/guides/logical-names.md#switching-the-view) נשלחת, וה[נעילה](../../guide/guides/settings.md#lock) שלה קובעת מה העורכים האחרים עושים איתה. הנעילה `Name View` מופעלת בתרשים חדש ובכל מסמך מלפני גרסה `4.2.0`.  
כל עוד הנעילה מופעלת, ההחלפה מוצגת רק בעורך שביצע אותה: היא עדיין נשלחת, אבל כל עורך אחר וכל רפליקה משליכים אותה, כך שכל משתמש יכול לצפות בתצוגה אחרת בזמן ש-`value` שומר את התצוגה הנעולה. שינוי של שפת הקוד, של סגנון שמות או של סוג המירכאות שונה: הוא מגיע לכל עורך, בין שהנעילה שלו מופעלת ובין שלא.  
כל עוד הנעילה כבויה, החלפה שבוצעה בעורך שמאפשר עריכה משנה את תצוגת השמות בכל עורך ובכל רפליקה, כשההחלפה האחרונה גוברת, וכל אחד מהם שומר אותה.  
החלפה שעורך לקריאה בלבד מבצע בעצמו נשארת תמיד באותו עורך, והעורך עדיין עוקב אחרי ההחלפות המשותפות של האחרים.

החל מגרסה `5.0.0`, עורך [לקריאה בלבד](../erd-editor-element.md#readonly) אינו שולח שום שינוי. הגלילה, הזום, הכרטיסייה, תצוגת השמות, מסד הנתונים, שפת מחולל הקוד, סגנונות השמות, סוג המירכאות ושורות `View Option` שהקורא משנה נשארים על המסך שלו, יהיו הנעילות שלהם אשר יהיו; לפני גרסה `5.0.0` הגלילות, הזומים, החלפות הכרטיסיות, מסד הנתונים והגדרות הקוד שלו נשלחו כמו אלה של עורך שמאפשר עריכה.  
המאגר שלו עדיין שולח את מה שהמעקבים שלו שולחים מהסמן, מהמיקוד, מהבחירה ומתיבת הגרירה של הקורא, עונה על הרגיסטרים שעורך מצטרף מבקש, ומחיל כל שינוי שהאחרים שולחים. שינוי של מסד הנתונים, של הגדרת מחולל קוד או של שורת `View Option` מגיע למסמך שלו, ולמסך שלו גם כן, אלא אם הקורא שינה את ההגדרה הזו שם, והחלפה משותפת של תצוגת השמות מוצגת על המסך שלו בכל מקרה.  
ברגע שהעורך הופך לקריאה בלבד הוא שולח תחילה את מה שהמאגר עדיין מעכב מגרירה או מגלילה, כפי ש-[flushStreamBuffers](#flushstreambuffers) עושה, כך שהאחרים שומרים את סופה.

[נעילות](../../guide/guides/settings.md#lock) הן משותפות: הנעילה או ביטול הנעילה האחרונים של הגדרה גוברים בכל עורך, ונעילה נושאת את הערכים של העורך שהפעיל אותה, כך שכל עורך וכל רפליקה שומרים את אותו ערך.  
לכן נעילת `Viewport` שומרת את התצוגה של העורך שהפעיל אותה, ונעילת `Canvas Type` את הכרטיסייה האחרונה שבה היה העורך הזה לפני כרטיסיית הגדרות, שבה מפעילים נעילות.  
ביטול הנעילה של `Language`, `Table Name Case`, `Column Name Case`, `Bracket Type` או, החל מגרסה `4.2.0`, `Name View` גם קובע את ההגדרה הזו בכל עורך לערך שמוצג בעורך שביטל אותה, כך שכל העורכים ממשיכים לשמור ערך אחד. ביטול הנעילה של `Viewport` או `Canvas Type` אינו מזיז את התצוגה או את הכרטיסייה של אף אחד.

עריכה של הסקריפט `Before tables` או `After tables` נשלחת בשלמותה כשהשדה שלו מאבד את הפוקוס. כל אחד משני הסקריפטים מוכרע בנפרד, כך שעריכה של שותף לעריכה באחד מהם לעולם אינה דורסת את השני.

שום דבר שנעשה ב[מצב זרימה](../../guide/guides/visualization.md#flow-never-edits-the-document) של כרטיסיית ויזואליזציה אינו שינוי במסמך, ולכן עורך שנמצא במצב זרימה אינו שולח לאחרים שום שינוי, והשינויים שהם שולחים ממשיכים לחול עליו כל עוד הוא שם.  
יש שני חריגים. יציאה ממצב זרימה לכרטיסייה אחרת היא החלפת כרטיסייה, שנשלחת כמו כל החלפה אחרת. החל מגרסה `4.2.0`, בחירה ברשימת תצוגת השמות בסרגל הכלים של מצב הזרימה היא החלפה של תצוגת השמות, שנשלחת ומוחלת כמו החלפה שבוצעה בבד הציור.  
הלחצנים `Previous table` ו-`Next table` ומקשי ביטול הפעולה והביצוע החוזר, ש[צועדים בין התצוגות](../../guide/guides/visualization.md#previous-table-and-next-table) במצב זרימה, אינם נשלחים.  
לחצן הקישור החיצוני בכרטיס, תוצאה של ה[חיפוש המהיר](../../guide/guides/quick-search.md#searching-the-diagram) שנבחרה אחרי `#`, `@` או `:`, ופתיחת ה[סייר](../../guide/guides/explorer.md#opening-and-closing) מעבירים כולם ממצב זרימה אל כרטיסיית ERD. גם גלילה שלחצן הכרטיס או תוצאה של החיפוש המהיר מבצעים שם נשלחת.

## שני עורכים בדף אחד {#two-editors-on-one-page}

החיבור מ-subscribe אל dispatch שכאן ממלא את מקום הרשת, כך שניתן לראות את צורת הסשן בלי ששכבת תעבורה מפריעה.

```js
import '@dineug/erd-editor/erd-editor.js';

const editor1 = document.createElement('erd-editor');
const editor2 = document.createElement('erd-editor');

const sharedStore1 = editor1.getSharedStore({
  getNickname: () => 'editor1',
});
const sharedStore2 = editor2.getSharedStore({
  getNickname: () => 'editor2',
});

sharedStore1.subscribe(actions => {
  sharedStore2.dispatch(actions);
});

sharedStore2.subscribe(actions => {
  sharedStore1.dispatch(actions);
});
```

שני העורכים כאן מתחילים מאותו מסמך חדש וריק, כך שאין צורך לאתחל אף אחד מהם.  
עם שלושה עורכים או יותר, יש לשלוח את האצוות של כל אחד מהם לכל האחרים: עורך לעולם אינו מעביר הלאה את מה שקיבל.

## אתחול שותף לעריכה {#seeding-a-collaborator}

מאגר משותף מעביר הלאה שינויים בזמן שהם נעשים ולעולם אינו מוסר למצטרף את המסמך במצבו הנוכחי, ולכן יש למסור תחילה את המסמך לעורך שמצטרף לסשן שכבר פועל.  
החל מגרסה `4.0.0`, יש לאתחל אותו באמצעות [`runtimeValue`](../erd-editor-element.md#runtimevalue) של עורך שכבר נמצא בסשן, ולא באמצעות `value` או הקובץ השמור.

```js
editor2.setInitialValue(editor1.runtimeValue);

const sharedStore2 = editor2.getSharedStore();
```

ערך זמן הריצה עדיין מכיל את מה שהוסר מאז שהמסמך נפתח, כך שכאשר עורך אחר מבטל מאוחר יותר הסרה, המצטרף מחזיר את הטבלה עם השם והעמודות שלה.  
[`value`](../erd-editor-element.md#value) הוא הצורה שנשמרת בקובץ, ללא ישויות שהוסרו, ולכן מצטרף שאותחל ממנו, או מהקובץ, היה מחזיר במקום זאת טבלה ריקה וללא שם.  
החל מגרסה `4.2.0`, אותו הדבר נכון גם למילה, למונח או לתחום שהוסרו מגיליון בכרטיסיית [מילון](../../guide/guides/dictionary.md): כשעורך אחר מבטל את ההסרה, מצטרף שאותחל מ-`runtimeValue` מחזיר את השורה לרשימה בשלמותה, ומצטרף שאותחל מ-`value` מחזיר שורה ריקה, שה-`value` שלו עצמו משמיט לאחר מכן.  
יש להמשיך לכתוב את `value` לאחסון: `runtimeValue` נועד רק לאתחול עורך אחר, תצוגה שנייה או [replicationStore](./remote-storage.md).  
העורכים ב-VS Code, ב-Obsidian, ב-IDE של JetBrains ובאפליקציית הרשת מאתחלים כך תצוגה שנייה של מסמך פתוח.

הקריאה ל-`setInitialValue` אינה מועברת הלאה, ולכן אתחול המצטרף אינו משנה דבר אצל האחרים.  
החל מגרסה `4.0.0`, היא גם משליכה את אוגרי שיתוף הפעולה של העורך, שמכריעים בין עריכות מקבילות. אם למאגר המשותף של העורך כבר היה מנוי, המאגר מבקש שוב מהעורכים האחרים את האוגרים שלהם, כמו בקריאה הראשונה שלו ל-[subscribe](#subscribe), כך שעורך שנטען מחדש באמצע סשן מכריע בין עריכות כפי שהאחרים מכריעים.  
השמה ל-`value` שומרת על האוגרים, אבל בניגוד ל-`setInitialValue` היא מועברת הלאה: ברגע שיש לעורך מאגר משותף, כל עורך בסשן טוען את המסמך שהוצב, ולכן לעולם אין לאתחל מצטרף בדרך זו.

## שילוב גרסאות שונות {#mixing-releases}

עורך מחיל רק את סוגי הפעולות שהגרסה שלו מכירה, ולכן בסשן שמשלב גרסאות שונות, העורכים הישנים יותר מפספסים כל מה שנשלח בסוג פעולה חדש יותר.

החל מגרסה `3.10.0`, שינוי של [ON DELETE או ON UPDATE](../../guide/guides/relationship-editing.md#on-delete-and-on-update) של קשר עובר כאחד משני סוגי פעולות חדשים, `relationship.changeOnDelete` ו-`relationship.changeOnUpdate`, והפעולה `relationship.add` יכולה לשאת את שניהם. מנגנון העברה שמעביר פעולות כמות שהן אינו צריך דבר חדש עבורם.  
עורך בגרסה שקודמת ל-`3.10.0` מתעלם מסוגי הפעולות ומהשדות האלה: הוא לעולם אינו יודע מה ה-ON DELETE או ה-ON UPDATE של קשר, ומסמך שנשמר ממנו אינו כולל אף אחד מהם. קשר שעורך ישן יותר מוסיף מגיע בלעדיהם, ולכן שניהם מתחילים ב-`Not set`.

כל שינוי אחר שעורך בגרסה `3.10.0` שולח עובר בסוגי פעולות שעורכים ישנים יותר כבר מכירים.  
הלחצן `Replace All` ב[איתור והחלפה](../../guide/guides/find-and-replace.md#replacing) שולח את העריכות שלו כאצווה אחת של אותן פעולות שינוי שם, הערה ופתק שעריכה ידנית שולחת. [אפשרויות התצוגה](../../guide/guides/table-related-functions.md#table-view-options) `Alternate Key` ו-`Referential Actions` עוברות בפעולה הקיימת `settings.changeShow`.

החל מגרסה `4.0.0`, השינויים הבאים עוברים בסוגי פעולות חדשים, ומנגנון העברה שמעביר פעולות כמות שהן אינו צריך דבר חדש עבורם:

- [קבוצת טבלאות](../../guide/guides/table-groups.md) שנוספה, שהוזזה, שגודלה שונה, ששמה שונה, שצבעה שונה או שהוסרה: `tableGroup.add`, `tableGroup.move`, `tableGroup.moveTo`, `tableGroup.resize`, `tableGroup.changeName`, `tableGroup.changeColor` ו-`tableGroup.remove`; טבלה שמצטרפת לקבוצה או עוזבת אותה: `table.changeGroup`;
- לחיצה על `Save` ב[מיפוי עמודות](../../guide/guides/relationship-editing.md#map-columns) של קשר קיים, שקובעת את שתי רשימות העמודות שלו בבת אחת: `relationship.changeColumns`;
- [נעילה](../../guide/guides/settings.md#lock) שהופעלה או בוטלה: `settings.changeLockSettings`;
- עריכה של הסקריפט `Before tables` או `After tables` בכרטיסיית [סכמת SQL](../../guide/guides/schema-sql.md): `settings.changeDDLScript`.

אפשרויות התצוגה `Table Groups` ו-`Memos` עוברות בפעולה הקיימת `settings.changeShow`.  
הפעולה `settings.changeIgnoreSaveSettings`, שהמתגים `Save Scroll Information` ו-`Save Zoom Information` שלחו לפני שהנעילות החליפו אותם, כבר אינה נשלחת, והפעולה `settings.changeRelationshipOptimization` הוסרה. עורך בגרסה `4.0.0` שמקבל אחת מהן אינו משנה דבר.

עורך בגרסה שקודמת ל-`4.0.0` מתעלם מסוגי הפעולות החדשים: הוא לעולם אינו רואה קבוצת טבלאות או אילו טבלאות נמצאות בה, אם כי גרירת קבוצה עדיין מזיזה בו את הטבלאות של הקבוצה, כי היא שולחת גם את `table.move` שלהן.  
הוא שומר את העמודות הישנות של קשר אחרי לחיצה על `Save` במיפוי עמודות, וכשעמודה מהמיפוי הישן הזה מוסרת בו, הקשר נעלם בכל העורכים. אין בו נעילות ואין בו סקריפטים.  
מסמך שנשמר ממנו אינו כולל אף אחד מאלה, ועורך בגרסה `4.0.0` פותח אותו כשכל הנעילות מופעלות.  
יש לוודא שכל עורך בסשן, וכל [replicationStore](./remote-storage.md#dispatch-dispatchsync) שמאחסן את המסמך שלו, נמצאים בגרסה `4.0.0` ומעלה.

עורך בגרסה `4.1.0` אינו שולח אף סוג פעולה חדש, ולכן עורכים ורפליקות בגרסאות `4.0.0` ו-`4.1.0` חולקים סשן בלי לפספס דבר.  
התכונה [איתור והחלפה](../../guide/guides/find-and-replace.md#replacing) שלו מחפשת גם בשמות אינדקסים ובשמות קבוצות טבלאות, והלחצנים `Replace` ו-`Replace All` משנים את שמותיהם באמצעות הפעולות `index.changeName` ו-`tableGroup.changeName`, שעורך בגרסה `4.0.0` כבר מחיל.

החל מגרסה `4.2.0`, השינויים הבאים עוברים בסוגי פעולות חדשים, ומנגנון העברה שמעביר פעולות כמות שהן אינו צריך דבר חדש עבורם:

- ה[שם הלוגי](../../guide/guides/logical-names.md) של טבלה או של עמודה: `table.changeLogicalName` ו-`column.changeLogicalName`; האם השם שלה [נגזר מהמילונים](../../guide/guides/dictionary.md#deriving-physical-names): `table.changeNameDerived` ו-`column.changeNameDerived`;
- עמודה שמקושרת ל[תחום](../../guide/guides/dictionary.md#domains-and-data-types) או שהקישור שלה מבוטל: `column.changeDomain`;
- מילה, מונח או תחום שנוספו, שהשתנו (כולל המיקום שלהם בגיליון, כפי שמיון קובע אותו) או שהוסרו בכרטיסיית [מילון](../../guide/guides/dictionary.md): `dictionary.add`, `dictionary.update` ו-`dictionary.remove`;
- החלפה של [תצוגת השמות](../../guide/guides/logical-names.md#switching-the-view): `settings.changeNameViewMode`.

הנעילה `Name View` עוברת בפעולה הקיימת `settings.changeLockSettings`, אפשרות התצוגה `Domain` בפעולה `settings.changeShow`, והזזה של `Logical Name` או של `Domain` ב[סדר העמודות](../../guide/guides/settings.md#adjusting-column-order) בפעולה `settings.changeColumnOrder`.  
הפעולות `editor.clear` ו-`editor.loadJson` של ייבוא סכמת SQL, GraphQL, DBML או AML מ-`Import` נושאות את `keepDictionaries: true`, ששומר את המילים, המונחים והתחומים בכל עורך. כך גם הפעולות של קריאה ל-[setSchemaSQL](../erd-editor-element.md#setschemasql), ל-`setSchemaGraphQL`, ל-`setSchemaDBML` או ל-`setSchemaAML` במצב החלפה.  
שם פיזי שהמילונים גוזרים עובר בפעולה `table.changeName` או `column.changeName`, וסוג הנתונים שתחום נותן לעמודות שלו עובר בפעולה `column.changeDataType`, אותן פעולות שעריכה ידנית שולחת.

עורך בגרסה שקודמת ל-`4.2.0` מתעלם מסוגי הפעולות החדשים: אין בו שמות לוגיים, קישורים לתחומים, מילונים או תצוגת שמות. נעילה או ביטול נעילה של `Name View` אינם משנים בו דבר, וכך גם הזזה של `Logical Name` או של `Domain` בסדר העמודות, או הזזה אל אחד מהם. גם נעילת `Canvas Type` שהופעלה על ידי עורך שהגיע לכרטיסיית הגדרות מכרטיסיית מילון אינה משנה בו דבר: העורך הישן יותר אינו מכיר את הכרטיסייה הזו, ולכן הוא משאיר את ההגדרה `Canvas Type` לא נעולה. הוא עדיין מציג את השמות הפיזיים שהמילונים גוזרים ואת סוגי הנתונים שתחומים נותנים.  
העריכות שלו עצמו אינן יודעות דבר על שמות לוגיים, תחומים או המילונים, ולכך יש ההשפעות הבאות על העורכים החדשים יותר:

- בטבלה או בעמודה שהוא משנה את שמה ידנית, השם נשאר מסומן כנגזר, ולכן שם לוגי שנכתב עבורה מאוחר יותר בעורך חדש יותר יכול לגזור את השם מחדש ולדרוס את השם שהעורך הישן הקליד.
- סוג נתונים שהוא נותן לעמודה שמקושרת לתחום משאיר את הקישור, ולכן הגיליון `Checks` מציג את `Domain type mismatch`, והשינוי הבא בסוג של התחום נותן לעמודה שוב את הסוג של התחום.
- עמודות המפתח הזר של קשר שהוא מוסיף אינן מקבלות שם לוגי או תחום מהמפתח שלהן.
- טבלה שהוא מדביק או משכפל מגיעה בלי שמות לוגיים ובלי קישורים לתחומים.
- ייבוא של סכמת SQL, GraphQL, DBML או AML בו אינו שולח את `keepDictionaries`, ולכן הוא מרוקן את המילים, המונחים והתחומים בכל עורך.
- ביטול של טעינה, של ייבוא או של `clear()` בו טוען בכל עורך את העותק שלו של המסמך, ובעותק הזה אין שמות לוגיים, קישורים לתחומים או מילונים.
- העותק הזה, והמסמך שייבוא של סכמת SQL, GraphQL, DBML או AML בו טוען, גם מחזירים את הנעילה `Name View` בכל עורך למצב שבו העורך הישן מצא אותה. לאחר מכן כל עורך שומר את `Physical Names` כתצוגת השמות, וגם מציג אותה אם הנעילה כבויה.

מסמך שנשמר מעורך כזה אינו כולל שמות לוגיים, קישורים לתחומים, מילונים או תצוגת שמות, ולכן עורך בגרסה `4.2.0` פותח אותו בתצוגה `Physical Names`. העורך הישן יותר כן שומר את הנעילה `Name View` כפי שמצא אותה, כך שמסמך שהנעילה שלו בוטלה בעורך בגרסה `4.2.0` נשאר לא נעול.  
יש לוודא שכל עורך בסשן, וכל [replicationStore](./remote-storage.md#dispatch-dispatchsync) שמאחסן את המסמך שלו, נמצאים בגרסה `4.2.0` ומעלה.

## SharedStoreConfig {#sharedstoreconfig}

### getNickname {#getnickname}

קובע את הכינוי שמוצג ליד סמן העכבר של המשתמש הזה בעורכים האחרים.  
משתמשים אחרים רואים `user` כשהכינוי חסר או ריק.

```js
editor.getSharedStore({
  getNickname: () => 'nickname...',
});
```

### mouseTracker {#mousetracker}

משדר את סמן העכבר של המשתמש הזה לעורכים האחרים. ברירת המחדל היא `true`.  
סמני עכבר שנשלחים על ידי משתמשים אחרים מוצגים תמיד על בד הציור של ERD.

```js
editor.getSharedStore({ mouseTracker: false });
```

### focusTracker {#focustracker}

משדר את מה שהמשתמש הזה עובד עליו. ברירת המחדל היא `true`.  
הטבלה שבפוקוס והתא הפעיל, הטבלאות, הפתקים וקבוצות הטבלאות שנבחרו, ומלבן הבחירה שגוררים על בד הציור נשלחים לעורכים האחרים ומוצגים בהם.  
כל משתמש מקבל צבע משלו, כך שניתן להבחין ביניהם: מסגרת סביב הטבלה שבפוקוס, קו תחתון מתחת לתא הפעיל, טבעת סביב הטבלאות, הפתקים וקבוצות הטבלאות שנבחרו, ומלבן מקווקו שמייצג את מלבן הבחירה.  
החל מגרסה `4.2.0`, כל משתמש יכול לצפות ב[תצוגת שמות](../../guide/guides/logical-names.md#collaborators) אחרת כל עוד הנעילה שלה מופעלת, או אחרי החלפה שעורך לקריאה בלבד ביצע בעצמו. תא פעיל שהתצוגה הנוכחית אינה מציגה מסומן בקו תחתון על התא שהיא מציגה במקומו: השם והשם הלוגי באים זה במקום זה, כמו סוג הנתונים והתחום.  
נוכחות שמגיעה ממשתמשים אחרים מוצגת תמיד על בד הציור של המשתמש, בין אם האפשרות הזו מופעלת ובין אם לא.  
במצב זרימה של כרטיסיית ויזואליזציה, הפוקוס והבחירה של משתמשים אחרים מוצגים על כרטיסי הטבלאות, אבל מלבני הבחירה שלהם אינם מוצגים. הטבלאות שבוחרים שם עדיין נשלחות; מלבן הבחירה שגוררים שם אינו נשלח.

```js
editor.getSharedStore({ focusTracker: false });
```

כדי להשתמש במאגר המשותף כמנגנון העברה פשוט שאינו מפרסם נוכחות משלו, יש לכבות את שני רכיבי המעקב.  
נוכחות שנשלחת מעורכים אחרים עדיין מתקבלת ומוצגת.  
כך פועלים העורכים ב-VS Code, ב-Obsidian, ב-IDE של JetBrains וב-Google Drive.

```js
editor.getSharedStore({ mouseTracker: false, focusTracker: false });
```

סמן העכבר, הפוקוס, הבחירה ומלבן הבחירה עוברים באותו זרם כמו השינויים במסמך, אבל הם ארעיים.  
הם לעולם אינם נכנסים למסמך, להיסטוריית הפעולות או ל-`editor.value`, ולכן שכבת התעבורה רשאית להשמיט אותם, ו-replicationStore מתעלם מהם.

## SharedStore {#sharedstore}

### connection, disconnect {#connection-disconnect}

מתודות אלה קובעות את מצב החיבור הנוכחי.  
בזמן שהחיבור מנותק, השינויים נאגרים באופן פנימי.  
השינויים שנאגרו משוגרים למנויים ברגע שאפשר לשלוח שוב.  
מצב ברירת המחדל הוא מחובר (`connection`).

```js
sharedStore.connection();
sharedStore.disconnect();
```

### dispatch, dispatchSync {#dispatch-dispatchsync}

מחילות שינויים ממופעי עורך אחרים על מופע העורך הנוכחי.

```js
sharedStore.dispatch(actions); // async
sharedStore.dispatchSync(actions); // sync
```

### subscribe {#subscribe}

נרשמת לשינויים בעורך.  
שום דבר אינו יוצא מהעורך עד שיש לפחות מנוי אחד, ושינויים שנעשים לפני כן נאגרים.  
ההרשמה הראשונה גם מבקשת מהעורכים האחרים את אוגרי שיתוף הפעולה שלהם, שמכריעים בין עריכות מקבילות, כך שמצטרף מאוחר מכריע ביניהן באותו אופן.  
היא אינה מביאה את המסמך, ולכן יש תחילה [לאתחל](#seeding-a-collaborator) מצטרף מאוחר.  
החל מגרסה `4.0.0`, המאגר מבקש שוב בכל פעם ש-`setInitialValue` טוענת מסמך לעורך שלו אחרי ההרשמה הראשונה הזו.

```js
const unsubscribe = sharedStore.subscribe(actions => {
  // send...
});
```

### flushStreamBuffers {#flushstreambuffers}

שולחת עכשיו את אצוות הזרם שהמאגר הזה עדיין מעכב, במקום אחרי תקופת השקט שלהן.  
החל מגרסה `3.9.2`, היא פועלת במאגר שמתקבל מ-`getSharedStore`; בגרסה `3.9.1` המתודה קיימת בטיפוס אך אינה עושה דבר.  
הזזת טבלה, פתק או קבוצת טבלאות, שינוי הצבע שלהם, שינוי גודל של פתק, וגלילה או זום של התצוגה מגיעים כל אחד כזרם של שינויים קטנים. שינוי גודל של קבוצת טבלאות אינו מגיע כך: הוא נשלח פעם אחת, כשהגרירה מסתיימת.  
המאגר אוסף כל זרם לאצווה אחת ומעכב אותה עד שהזרם שקט במשך 200ms. הוא עושה זאת בשני שלבים, כך שהאצווה יוצאת כ-400ms אחרי השינוי האחרון.  
קריאה מסיימת את ההמתנה הזו בשני השלבים. כל עוד המאגר מחובר, מנוי מקבל את האצווה לפני שהקריאה חוזרת. קריאה כשאין דבר מעוכב אינה שולחת דבר.  
המתודה `destroy`, של המאגר עצמו או של העורך, מוחקת אצווה שעדיין מעוכבת, ולכן יש לקרוא קודם ל-flushStreamBuffers כשמשחררים מאגר והאחרים אמורים לשמור את השינוי האחרון, כמו כשכרטיסייה נסגרת.

```js
sharedStore.flushStreamBuffers();
sharedStore.destroy();
```

### destroy {#destroy}

משמידה לחלוטין את מופע ה-sharedStore.  
העורך עצמו אינו מושפע, כך שאחרי עזיבת סשן עדיין ניתן לערוך את המסמך.  
רכיבי המעקב אחר העכבר והפוקוס נעצרים ברגע שה-sharedStore האחרון שהעורך מסר מושמד.  
אצוות זרם שהמאגר עדיין מעכב נמחקת יחד איתו; כדי לשלוח אותה, יש לקרוא תחילה ל-[flushStreamBuffers](#flushstreambuffers).

```js
sharedStore.destroy();
```
