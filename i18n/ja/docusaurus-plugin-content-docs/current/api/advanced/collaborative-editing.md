# 共同編集

`getSharedStore()` は、エディタを共同編集セッションのノードにします。  
すべての変更をアクションのストリームとして発行し、他のエディタから送られてきたアクションを適用します。エディタ間をつなぐトランスポート（WebSocket、WebRTC、その他 JSON を運べるもの）は利用者側で用意します。  
[ErdEditorElement](../erd-editor-element.md) のメソッドの 1 つで、中継した変更を保存する必要がある場合は[リモート保存](./remote-storage.md)と組み合わせて使います。  
`5.1.0` からは、トランスポートを自分で用意する代わりに Yjs ドキュメントとそのいずれかのプロバイダを通してダイアグラムを共有するには、`@dineug/erd-editor-yjs` でエディタをバインドします。[Yjs](./yjs.md) を参照してください。

```ts
interface ErdEditorElement extends HTMLElement {
  // ...
  getSharedStore: (
    config?: SharedStoreConfig & {
      mouseTracker?: boolean;
      focusTracker?: boolean;
    }
  ) => SharedStore;
}

type SharedStoreConfig = {
  getNickname?: () => string;
};

type SharedStore = {
  connection: () => void;
  disconnect: () => void;
  dispatch: (actions: Array<AnyAction> | AnyAction) => void;
  dispatchSync: (actions: Array<AnyAction> | AnyAction) => void;
  subscribe: (fn: (value: AnyAction[]) => void) => Unsubscribe;
  flushStreamBuffers: () => void;
  getLWW: () => SharedRegisters;
  mergeLWW: (lww: SharedRegisters, version: number) => void;
  getVersion: () => number;
  forgetPeer: (editorId: string) => void;
  reseed: (value: string, options: ReseedOptions) => void;
  destroy: () => void;
};

// a JSON object whose shape is the editor's own: hand it on as it is
type SharedRegisters = Record<string, unknown> & {
  readonly [registersBrand]: true;
};

type ReseedOptions = {
  lww: SharedRegisters;
  version: number;
  keepScreen?: boolean; // default false
};

// example
const sharedStore = editor.getSharedStore();
```

`@dineug/erd-editor` はこれらの型を名前付きではエクスポートしません。TypeScript のコードでは、`ReturnType<ErdEditorElement['getSharedStore']>` のように `ErdEditorElement` を通して参照します。

アクションはドキュメントへの 1 つの変更を表す単純なシリアライズ可能なオブジェクトであり、トランスポートへ渡す途中で `JSON.stringify` を通しても壊れません。  
アクションはバッチで届き、`subscribe` が渡す配列が 1 つの単位となるため、配列全体をそのまま中継し、受け取り側でも配列全体をそのまま dispatch します。  
アクションが持つ管理情報（その[バージョン](#concurrent-edits)など）がエディタ間の同期を支えているため、内容を読んだり書き換えたりせず、不透明な値としてそのまま受け渡します。

エディタで行う操作の中には、そのエディタだけにとどまるものがあります。  
選択したときのようにテーブル、メモ、テーブルグループを前面に移しても、それは送信されません。  
[Schema SQL](../../guide/guides/schema-sql.md) タブの `Statements`、`Header`、`Write logical names into empty comments`（`4.2.0` から）、`Tables` の選択も、それを選んだウィンドウに属するため、送信されません。  
`4.1.0` からは、[エクスプローラー](../../guide/guides/explorer.md)もそのエディタだけにとどまります。開いているかどうか、幅、折りたたんだ行、キーボードの行、ツリーのスクロールの位置、検索とオプションは送信されません。  
外部キーへ移動したときにそのリレーションシップのコネクタに付く[強調表示](../../guide/guides/relationship-editing.md#reading-a-connector)も送信されません。  
`4.2.0` からは、[辞書](../../guide/guides/dictionary.md)タブもそのエディタだけにとどまります。どのシートを表示しているか、各シートの検索、選択、スクロール、列幅は送信されません。辞書タブでの編集、並べ替え、CSV の読み込みは送信されます。  
スクロール、拡大・縮小、タブの切り替えは送信されますが、他のユーザーのビューやタブを動かすことはありません。エクスプローラーからの移動で行われるスクロール、別のタブからエクスプローラーを開いたときの ERD タブへの切り替え、辞書タブの [`Checks`](../../guide/guides/dictionary.md#the-checks-sheet) シートからテーブルやカラムへ移動したときのタブの切り替えとスクロールも同じです。そのシートから単語、用語、ドメインへの移動は辞書タブの中にとどまるため、どれも送信されません。

`4.2.0` からは、[名前の表示](../../guide/guides/logical-names.md#switching-the-view)の切り替えも送信され、他のエディタがそれをどう扱うかは、その[ロック](../../guide/guides/settings.md#ロック)で決まります。`Name View` のロックは、新しいダイアグラムと、`4.2.0` より前のすべてのドキュメントでオンになっています。  
ロックがオンの間は、切り替えはそれを行ったエディタにだけ反映されます。切り替え自体は送信されますが、他のすべてのエディタとすべてのレプリカはそれを破棄するため、`value` がロックした表示を保ったまま、ユーザーごとに異なる表示を見ることができます。  
ロックがオフの間は、編集できるエディタで行った切り替えによって、すべてのエディタとレプリカの名前の表示が変わります。最後に行われた切り替えが有効になり、どのエディタとレプリカもその表示を保存します。  
読み取り専用のエディタ自身の切り替えは常にそのエディタだけにとどまり、そのエディタも、他のエディタから共有される切り替えには引き続き従います。

`5.1.0` からは、[Code Generator](../../guide/guides/code-generator.md) の言語、テーブル名のケース、カラム名のケース、括弧の種類の変更も、それぞれのロック（`Language`、`Table Name Case`、`Column Name Case`、`Bracket Type`）に従って同じように扱われますが、1 つ違いがあります。ロックがオンの間は、変更がまったく送信されません。  
変更はそれを行ったエディタにだけ反映され、そのエディタの Code Generator タブと Schema SQL タブがそれに従います。他のエディタやレプリカにはそれが見えません。`value` と `runtimeValue` はロックした値を保つため、どのエディタから初期値を設定した参加者にもそれは見えず、ロックがオンの間は、ユーザーごとに異なる言語、名前のケース、括弧の種類を見ることができます。  
ロックがオフの間は、編集できるエディタで行った変更が、共有されたものとしてマークを付けて（そのペイロードの `shared: true`）送信されます。この変更によってすべてのエディタとレプリカの設定が変わります。最後に行われた変更が有効になり、どのエディタとレプリカもそれを保存します。`5.1.0` のエディタまたはレプリカは、自身のロックの状態にかかわらずマーク付きの変更を適用するため、ロックの解除の直後に行った変更は、ロックの解除より先に届く場合でも、どこでも反映されます。  
`5.1.0` より前は、そのような変更はロックがオンかどうかにかかわらずすべてのエディタとレプリカに届き、ファイルにはロックした値が保たれていました。

`5.0.0` からは、[読み取り専用](../erd-editor-element.md#readonly)のエディタは変更をまったく送信しません。その閲覧者が変更するスクロール、拡大・縮小、タブ、名前の表示、データベース、Code Generator の言語、名前のケース、括弧の種類、`View Option` の行は、ロックの状態にかかわらずそのエディタの画面にとどまります。`5.0.0` より前は、そのスクロール、拡大・縮小、タブの切り替え、データベース、コード設定が、編集できるエディタと同じように送信されていました。  
そのストアは、トラッカーが送る閲覧者のカーソル、フォーカス、選択、ドラッグボックスは引き続き送信し、参加するエディタが求めるレジスタに応答し、他のエディタが送るすべての変更を適用します。データベース、Code Generator の設定、`View Option` の行の変更はそのドキュメントに届き、閲覧者がその画面でその設定を変更していなければ画面にも届きます。共有された名前の表示の切り替えは、どちらの場合も画面に反映されます。`5.1.0` からは、Code Generator の設定は、ロックをオフにして変更されたとき、またはロックの解除がそれを伴うときにだけ届きます。  
エディタが読み取り専用になるとき、まずドラッグやスクロールについてストアがまだ保留している分を、[flushStreamBuffers](#flushstreambuffers) と同じように送信するため、他のエディタには最後の状態まで届きます。

[ロック](../../guide/guides/settings.md#ロック)は共有されます。設定ごとに最後に行われたロックまたはロックの解除がすべてのエディタで有効になり、ロックはそれをオンにしたエディタの値を伴うため、すべてのエディタとレプリカが同じ値を保存します。  
そのため、`Viewport` のロックはそれをオンにしたエディタのビューを保存し、`Canvas Type` のロックは、ロックをオンにする設定タブを開く前にそのエディタが最後に開いていたタブを保存します。  
`Language`、`Table Name Case`、`Column Name Case`、`Bracket Type`、または `4.2.0` からは `Name View` のロックをオフにすると、すべてのエディタのその設定も、ロックをオフにしたエディタに表示されている値（ロックの間にそのエディタで行った自身の変更を含みます）になるため、引き続き 1 つの値が保存されます。`Viewport` や `Canvas Type` のロックをオフにしても、誰のビューもタブも動きません。

`Before tables` または `After tables` のスクリプトの編集は、そのフィールドがフォーカスを失ったときに全体が送信されます。2 つのスクリプトはそれぞれ別に調停されるため、共同編集者が一方を編集しても、もう一方が上書きされることはありません。

Visualization タブの [Flow モード](../../guide/guides/visualization.md#flow-never-edits-the-document)で行う操作はどれもドキュメントの変更ではないため、Flow を表示しているエディタは他のエディタに変更を送らず、その間も他のエディタから送られてくる変更は引き続き適用されます。  
例外は 2 つあります。Flow から別のタブへ移ることはタブの切り替えであり、他のタブの切り替えと同じように送信されます。`4.2.0` からは、Flow のツールバーにある名前の表示の一覧での選択は名前の表示の切り替えであり、キャンバスで行った切り替えと同じように送信され、適用されます。  
Flow で[ビューを前後にたどる](../../guide/guides/visualization.md#previous-table-and-next-table)`Previous table`、`Next table`、Undo と Redo のキーは送信されません。  
カードの外部リンクボタン、`#`、`@`、`:` の後に選んだ[クイック検索](../../guide/guides/quick-search.md#searching-the-diagram)の結果、[エクスプローラー](../../guide/guides/explorer.md#opening-and-closing)を開く操作は、どれも Flow から ERD タブへ移ります。カードのボタンやクイック検索の結果がそこで行うスクロールも送信されます。

## 1 つのページに 2 つのエディタ

ここでの subscribe から dispatch への接続はネットワークの代わりであり、トランスポートを挟まずにセッションの形を確認できます。

```js
import '@dineug/erd-editor/erd-editor.js';

const editor1 = document.createElement('erd-editor');
const editor2 = document.createElement('erd-editor');

const sharedStore1 = editor1.getSharedStore({
  getNickname: () => 'editor1',
});
const sharedStore2 = editor2.getSharedStore({
  getNickname: () => 'editor2',
});

sharedStore1.subscribe(actions => {
  sharedStore2.dispatch(actions);
});

sharedStore2.subscribe(actions => {
  sharedStore1.dispatch(actions);
});
```

ここでは両方のエディタが同じ新しい空のドキュメントから始まるため、どちらにも初期値を設定する必要はありません。  
エディタが 3 つ以上ある場合は、各エディタのバッチを他のすべてのエディタへ送ります。エディタは受け取ったものを他のエディタへ転送しません。

## 参加者への初期値の設定

shared store は変更が行われるたびにそれを中継しますが、その時点のドキュメントを参加者に渡すことはありません。そのため、すでに進行中のセッションに参加するエディタには、先にドキュメントを渡す必要があります。  
`4.0.0` からは、`value` や保存されたファイルではなく、すでにセッションにいるエディタの [`runtimeValue`](../erd-editor-element.md#runtimevalue) で初期値を設定します。  
[`@dineug/erd-editor-yjs`](./yjs.md) でバインドしたルームは、クライアントが[初期値を設定](./yjs.md#seeding-a-room)すると、ドキュメントそのものを保持するため、そのルームにバインドしたすべてのエディタは、`runtimeValue` を渡さなくてもそのドキュメントを開きます。

```js
editor2.setInitialValue(editor1.runtimeValue);

const sharedStore2 = editor2.getSharedStore();
```

ランタイム値には、ドキュメントを開いてから削除されたものも残っているため、後で他のエディタが削除を Undo すると、参加したエディタでもテーブルが名前とカラムを持った状態で戻ります。  
[`value`](../erd-editor-element.md#value) はファイルが保持する形式で、削除されたエンティティを含まないため、`value` やファイルから初期値を設定した参加者では、代わりに名前のない空のテーブルが戻ります。  
`4.2.0` からは、[辞書](../../guide/guides/dictionary.md)のシートから削除した単語、用語、ドメインも同じです。他のエディタが削除を Undo すると、`runtimeValue` から初期値を設定した参加者ではその行が元どおりに表示され、`value` から初期値を設定した参加者では空の行が表示され、その参加者自身の `value` にはその行が含まれません。  
ストレージには引き続き `value` を書き込みます。`runtimeValue` は、別のエディタ、2 つ目のビュー、[replicationStore](./remote-storage.md) に初期値を設定するためだけのものです。  
VS Code、Obsidian、JetBrains IDE、Web アプリのエディタは、開いているドキュメントの 2 つ目のビューにこの方法で初期値を設定します。

`setInitialValue` は中継されないため、参加者に初期値を設定しても他のエディタでは何も変わりません。  
`4.0.0` からは、[同時に行われた編集](#concurrent-edits)を調停する、エディタの共同編集用のレジスタも破棄します。そのエディタの shared store にすでに購読者がいたことがある場合、store は最初の [subscribe](#subscribe) のときと同じように他のエディタにレジスタを改めて要求するため、セッションの途中で読み込み直したエディタも、他のエディタと同じように編集を調停します。  
`value` への代入はレジスタを保持しますが、`setInitialValue` とは異なり中継されます。エディタが shared store を持つと、セッション内のすべてのエディタが代入したドキュメントを読み込むため、この方法で参加者に初期値を設定しないでください。

`value` と `runtimeValue` のどちらにも、レジスタと、エディタのクロックが到達したバージョンは含まれないため、`runtimeValue` だけで初期値を設定した参加者は、最初の subscribe に対してセッション内のエディタが送る応答からそれらを受け取ります。  
その応答が届くまでの間、参加者が行う編集は他のエディタが持つものより低いバージョンを伴うことがあり、その場合は参加者の手元にとどまったまま他のエディタに拒否され、まだ送信途中の古い書き込みが、初期値が持つ新しい書き込みを上書きします。サーバーやドキュメントストアがセッションのドキュメントを保持している場合のように、応答する実行中のエディタがなければ、参加者はそれらを受け取れません。  
`5.1.0` からは、それらを値と一緒に渡します。セッション内のエディタで [`flushStreamBuffers()`](#flushstreambuffers) を呼び出して、store がまだ保留しているドラッグや色の変更を先に送信し、その直後に `runtimeValue` と、そのエディタの store の [`getLWW()`](#getlww) および [`getVersion()`](#getversion) を同時に読み取ります。参加者は `setInitialValue` で値を読み込み、続けて自身の store の [`mergeLWW`](#mergelww) で残りを受け取ります。この順序を守るのは、`setInitialValue` が呼ばれるたびにレジスタが破棄されるためです。これにより参加者の次の編集は、初期値が持つすべてのバージョンを超えるバージョンを伴うため、応答を待たずに反映されます。すでに存在する store では、[`reseed`](#reseed) が両方を 1 回の呼び出しで行います。

```js
// on an editor already in the session
sharedStore1.flushStreamBuffers();
const seed = {
  value: editor1.runtimeValue,
  lww: sharedStore1.getLWW(),
  version: sharedStore1.getVersion(),
};

// on the joiner
editor2.setInitialValue(seed.value);
const sharedStore2 = editor2.getSharedStore();
sharedStore2.mergeLWW(seed.lww, seed.version);
```

後から参加するエディタのためにこの方法で保管しておく初期値は、この 3 つをまとめて保持します。これはファイルではありません。ストレージに書き込むのは引き続き `value` です。  
[replicationStore](./remote-storage.md#runtimevalue-getter) はレジスタを渡さないため、その `runtimeValue` から初期値を設定した参加者は、引き続きエディタからの応答でそれらを受け取ります。

## 同時編集 {#concurrent-edits}

すべてのエディタとレプリカは、名前とほぼすべてのフィールドについて、それを設定した書き込みのバージョンを保持しています。これが共同編集用のレジスタです。書き込みは、そのバージョンが保持しているバージョン以上のときにだけ反映されるため、同じ変更を異なる順序で受け取ったエディタも、同じドキュメントにたどり着きます。  
`5.1.0` からは、各バージョンはカウンタの下に、書き込んだエディタ固有のスロットを持ちます。スロットはそのエディタの ID から取られます。そのためバージョンは 4,194,304 刻みで増え、カウンタが 512 に達すると 32 ビット整数に収まらなくなります。`JSON.stringify` と `JSON.parse` はそれらをそのまま運びますが、別の言語でそれらを解析する中継やストアは、32 ビット整数ではなく 64 ビットの数値として保持する必要があります。

`5.1.0` からは、以下の例外を除き、1 つの名前またはフィールドを同時に変更した 2 つのエディタは、すべてのエディタとレプリカで同じ値になります。同じカウンタで書き込んでも 2 つの異なるバージョンが付き、大きいほうがどこでも有効になるためです。`5.1.0` より前は、両方が同じバージョンを付けることがあり、各エディタが最後に受け取ったほうを保持したため、結果が分かれることがありました。2 つのエディタが同じスロットを持つ確率は 1 組あたり 4,194,304 分の 1 で、その場合は以前と同じく、2 つのバージョンが等しくなります。

`5.1.0` からは、テーブルの位置、メモやテーブルグループの位置とサイズ、ビューの原点と拡大・縮小のレベルも同じようにバージョンが付けられ、それらを動かす操作は、行き着いた先として送信されます。

- ドラッグは、移動したエンティティごとに 1 つの `table.moveTo`、`memo.moveTo`、`tableGroup.moveTo` として 1 つのバッチで送信されるため、グループのドラッグはグループの位置にそのテーブルの位置を、`5.1.1` からはそのメモの位置も伴います。
- ドラッグの Undo または Redo は、各エンティティを置く位置として送信されます。
- パンは `settings.scrollTo`、拡大・縮小は `settings.changeZoomLevel` として送信されます。
- メモやテーブルグループのサイズ変更は、位置とサイズを一緒にして送信されます。

そのため、1 つのテーブル、メモ、テーブルグループを同時に移動した、または移動とサイズ変更をした 2 人のユーザーは、すべてのエディタとレプリカで同じ位置と同じサイズになります。位置は、バージョンが大きいほうの書き込みのものになり、両方の軸が一緒に決まります。移動はサイズを書き込まないため、同時に行われた移動が位置を取った場合でも、サイズ変更のサイズは保たれます。  
`5.1.0` より前は、ドラッグは移動した距離として送信されていたため、1 つのテーブルへの 2 つのドラッグは加算され、1 つのメモまたはテーブルグループに同時に行った移動とサイズ変更は、結果が分かれることがありました。  
20 px 未満のドラッグは Undo のエントリーを残しませんが、他のドラッグと同じように送信されるため、位置として、別のユーザーが同時に行った同じエンティティのドラッグを上書きすることがあります。トランスポートが 2 回届けたドラッグ、パン、拡大・縮小のバッチは、2 回動かすことはありません。

色の変更は例外です。バージョンなしで送信され、各エディタとレプリカが自身のバージョンを付けて最後に受け取った色を保持するため、1 つのテーブル、メモ、テーブルグループの色を同時に変更した 2 人のユーザーは、異なる色になることがあります。  
バージョンをまったく持たない変更がいくつかあり、各エディタとレプリカはそれらを受け取った順に適用するため、同時に行われた 2 つの変更は、やはり結果が分かれることがあります。テーブルまたはインデックスの中でのカラムの移動（`column.move`、`indexColumn.move`）、[データベース](../../guide/guides/table-related-functions.md#databases)、[`View Option`](../../guide/guides/table-related-functions.md#table-view-options) の行、[設定](../../guide/guides/settings.md)タブの `Relationship DataType Sync`、`Maximum comment width`、`Column Order` の変更です。  
2 人のユーザーが同時に追加したエンティティ、例えば 2 つのテーブルや、1 つのテーブルの 2 つのカラムは、エディタとレプリカごとに異なる順序で並ぶことがあり、それぞれの `value` は自身の順序を保存します。

これらはすべて `5.1.0` 以降のエディタとレプリカの間で成り立ちます。それより古いものが加わった場合に何が変わるかは、[リリースの混在](#リリースの混在)を参照してください。

## リリースの混在

エディタは自身のリリースが知っているアクションの種類だけを適用するため、リリースが混在するセッションでは、古いエディタは新しい種類のアクションで送られる変更をすべて取りこぼします。

`3.10.0` からは、リレーションシップの [ON DELETE または ON UPDATE](../../guide/guides/relationship-editing.md#on-delete-and-on-update) の変更は、2 つの新しいアクションの種類 `relationship.changeOnDelete` と `relationship.changeOnUpdate` のいずれかとして送られ、`relationship.add` は両方を持つことができます。アクションをそのまま受け渡す中継であれば、これらのために新たに対応する必要はありません。  
`3.10.0` より前のエディタは、これらのアクションの種類とフィールドを無視するため、リレーションシップの ON DELETE も ON UPDATE も伝わらず、そのようなエディタで保存したドキュメントにはどちらも含まれません。古いエディタが追加したリレーションシップはこれらを持たずに届くため、どちらも `Not set` で始まります。

`3.10.0` のエディタが送るそれ以外の変更は、どれも古いエディタがすでに知っているアクションの種類で送られます。  
[検索と置換](../../guide/guides/find-and-replace.md#replacing)の `Replace All` は、手で編集したときと同じ名前の変更、コメント、メモのアクションを 1 つのバッチにまとめて送ります。`Alternate Key` と `Referential Actions` の[表示オプション](../../guide/guides/table-related-functions.md#table-view-options)は、既存の `settings.changeShow` アクションで送られます。

`4.0.0` からは、次の変更が新しいアクションの種類で送られます。アクションをそのまま受け渡す中継であれば、これらのために新たに対応する必要はありません。

- [テーブルグループ](../../guide/guides/table-groups.md)の追加、移動、サイズ変更、名前の変更、色の変更、削除: `tableGroup.add`、`tableGroup.move`、`tableGroup.moveTo`、`tableGroup.resize`、`tableGroup.changeName`、`tableGroup.changeColor`、`tableGroup.remove`。テーブルがグループに加わる、またはグループを離れる変更: `table.changeGroup`。
- 既存のリレーションシップでの [Map Columns](../../guide/guides/relationship-editing.md#map-columns) の `Save`（リレーションシップの両側のカラムのリストを一度に設定します）: `relationship.changeColumns`。
- [ロック](../../guide/guides/settings.md#ロック)のオンとオフ: `settings.changeLockSettings`。
- [Schema SQL](../../guide/guides/schema-sql.md) タブの `Before tables` または `After tables` のスクリプトの編集: `settings.changeDDLScript`。

`Table Groups` と `Memos` の表示オプションは、既存の `settings.changeShow` アクションで送られます。  
ロックに置き換えられる前に `Save Scroll Information` と `Save Zoom Information` のスイッチが送っていた `settings.changeIgnoreSaveSettings` は送信されなくなり、`settings.changeRelationshipOptimization` はなくなりました。`4.0.0` のエディタは、どちらを受け取っても何も変えません。

`4.0.0` より前のエディタは新しいアクションの種類を無視するため、テーブルグループも、どのテーブルがグループに含まれるかも知ることはありません。ただし、グループのドラッグはそのテーブルそれぞれの移動も送るため、そのエディタでもグループのテーブルは移動します。  
Map Columns の `Save` の後もリレーションシップの古いカラムを保持し、その古い対応付けのカラムがそのエディタで削除されると、リレーションシップはすべてのエディタから消えます。ロックもスクリプトもありません。  
そのようなエディタで保存したドキュメントにはこれらのどれも含まれず、`4.0.0` のエディタはそのドキュメントをすべてのロックがオンの状態で開きます。  
セッション内のすべてのエディタと、そのドキュメントを保存する [replicationStore](./remote-storage.md#dispatch-dispatchsync) には、`4.0.0` 以降を使います。

`4.1.0` のエディタは新しい種類のアクションを送らないため、`4.0.0` と `4.1.0` のエディタとレプリカは、何も取りこぼすことなく 1 つのセッションを共有できます。  
そのエディタの[検索と置換](../../guide/guides/find-and-replace.md#replacing)はインデックス名とテーブルグループ名も検索し、`Replace` と `Replace All` は、`4.0.0` のエディタがすでに適用している `index.changeName` と `tableGroup.changeName` のアクションでそれらの名前を変更します。

`4.2.0` からは、次の変更が新しいアクションの種類で送られます。アクションをそのまま受け渡す中継であれば、これらのために新たに対応する必要はありません。

- テーブルやカラムの[論理名](../../guide/guides/logical-names.md): `table.changeLogicalName` と `column.changeLogicalName`。その名前が[辞書から生成された](../../guide/guides/dictionary.md#deriving-physical-names)ものかどうか: `table.changeNameDerived` と `column.changeNameDerived`。
- カラムの[ドメイン](../../guide/guides/dictionary.md#domains-and-data-types)への紐付けとその解除: `column.changeDomain`。
- [辞書](../../guide/guides/dictionary.md)タブでの単語、用語、ドメインの追加、変更（並べ替えで決まる、シート内での位置を含みます）、削除: `dictionary.add`、`dictionary.update`、`dictionary.remove`。
- [名前の表示](../../guide/guides/logical-names.md#switching-the-view)の切り替え: `settings.changeNameViewMode`。

`Name View` のロックは既存の `settings.changeLockSettings` アクションで、`Domain` の表示オプションは `settings.changeShow` で、[カラム順](../../guide/guides/settings.md#adjusting-column-order)での `Logical Name` または `Domain` の移動は `settings.changeColumnOrder` で送られます。  
`Import` からの Schema SQL、GraphQL、DBML、AML の読み込みが送る `editor.clear` と `editor.loadJson` は `keepDictionaries: true` を持ち、すべてのエディタで単語、用語、ドメインを保ちます。置き換えを行う [setSchemaSQL](../erd-editor-element.md#setschemasql)、`setSchemaGraphQL`、`setSchemaDBML`、`setSchemaAML` が送るものも同じです。  
辞書が生成した物理名は `table.changeName` または `column.changeName` で、ドメインがそのカラムに与えるデータ型は `column.changeDataType` で送られます。どちらも手で編集したときに送られるアクションです。

`4.2.0` より前のエディタは新しいアクションの種類を無視します。そのエディタには論理名、ドメインの紐付け、辞書、名前の表示がありません。そこでは `Name View` のロックやその解除は何も変えず、カラム順での `Logical Name` や `Domain` の移動、またはそのどちらかの位置への移動も同様です。辞書タブから設定タブに来たエディタがオンにした `Canvas Type` のロックも何も変えません。古いエディタはそのタブを知らないため、`Canvas Type` のロックをオフのままにします。辞書が生成した物理名と、ドメインが与えたデータ型は引き続き表示されます。  
そのエディタ自身の編集は論理名、ドメイン、辞書について何も知らないため、新しいエディタには次のような影響があります。

- そのエディタで手で名前を変更したテーブルやカラムは、名前が生成されたものとして記録されたままになるため、後で新しいエディタでそれに論理名を書くと、手で入力した名前を上書きして名前が再び生成されることがあります。
- ドメインに紐付いたカラムにそのエディタでデータ型を与えても紐付けは残るため、`Checks` シートには `Domain type mismatch` が表示され、次にドメインのデータ型を変更すると、カラムには再びドメインのデータ型が与えられます。
- そのエディタで追加したリレーションシップの外部キーのカラムは、参照するキーから論理名もドメインも受け取りません。
- そのエディタで貼り付けたり複製したりしたテーブルは、論理名もドメインの紐付けもない状態で届きます。
- そのエディタでの Schema SQL、GraphQL、DBML、AML の読み込みは `keepDictionaries` を送らないため、すべてのエディタで単語、用語、ドメインが空になります。
- そのエディタでドキュメントの読み込み、ファイルの読み込み、`clear()` を Undo すると、すべてのエディタにそのエディタが持つドキュメントのコピーが読み込まれます。そのコピーには論理名、ドメインの紐付け、辞書がありません。
- そのコピーと、そのエディタで Schema SQL、GraphQL、DBML、AML を読み込んだときに読み込まれるドキュメントは、すべてのエディタの `Name View` のロックも、そのエディタがドキュメントを受け取ったときの状態に戻します。その後、すべてのエディタは名前の表示として `Physical Names` を保存し、ロックがオフの場合は表示も `Physical Names` になります。

そのようなエディタで保存したドキュメントには論理名、ドメインの紐付け、辞書、名前の表示が含まれないため、`4.2.0` のエディタはそのドキュメントを `Physical Names` で開きます。古いエディタは `Name View` のロックを受け取ったときのとおりに保存するため、`4.2.0` のエディタでロックをオフにしたドキュメントはオフのままです。  
セッション内のすべてのエディタと、そのドキュメントを保存する [replicationStore](./remote-storage.md#dispatch-dispatchsync) には、`4.2.0` 以降を使います。

`5.1.0` のエディタは新しい種類のアクションを送らないため、`5.1.0` より前のエディタとレプリカも引き続きそのエディタとセッションを共有でき、アクションをそのまま受け渡す中継であれば、新たに対応する必要はありません。ただし、[同時編集](#concurrent-edits)で説明した内容が成り立つのは、`5.1.0` のエディタとレプリカの間だけです。

- `5.1.0` のエディタのドラッグは、`table.moveTo`、`memo.moveTo`、`tableGroup.moveTo` の位置として送られ、これらは古いエディタもすでに適用します。パンと拡大・縮小は、`settings.scrollTo` と `settings.changeZoomLevel` の位置として送られ、すべてのパンと拡大・縮小と同じく、他のエディタは適用せず、レプリカだけが受け取ります。古いエディタは、ドラッグの各位置をレジスタの外で、届いた順に適用します。古いレプリカも、ドラッグ、パン、拡大・縮小の各位置を同じように適用するため、1 つのエンティティまたはビューに対して同時に送られた 2 つの位置は、そこで結果が分かれることがあります。
- 古いエディタのドラッグは、引き続き移動した距離として送られ、すべてのエディタとレプリカがレジスタの外で加算します。そのパンや拡大・縮小も距離として送られ、すべてのレプリカが同じように加算します。1 つのエンティティに対して同時に行われた距離と位置は、それらを異なる順序で受け取るエディタとレプリカで結果が分かれることがあり、トランスポートが 2 回届けた距離は 2 回加算されます。
- [同時編集](#concurrent-edits)が挙げる例外を除き、`5.1.0` のエディタが書き込んだ名前やフィールドが、古いエディタによる同時の書き込みと重なった場合は、ほぼ必ず `5.1.0` のエディタのものが有効になり、すべてのエディタとレプリカで同じ結果になります。古い 2 つのエディタが 1 つのフィールドを同時に書き込んだ場合は、やはり結果が分かれることがあります。
- `5.1.0` のエディタは、Code Generator の言語、名前のケース、括弧の種類の変更を、ロックがオフの間だけ、`shared: true` のマークを付けて送信します。古いエディタはこのマークを無視して、変更を従来どおり適用します。古いエディタは、ロックがオンの間に行った変更を、引き続きマークなしで送信します。`5.1.0` のエディタまたはレプリカは、その設定がそこでロックされている間はそれを破棄し、古いエディタは適用します。そのため、ロックの間は、古いエディタ同士は互いの選択に従い、`5.1.0` のエディタは自身の選択を保ちます。どちらの場合も、ファイルにはロックした値が保たれます。どちらのリリースで行ったロックの解除も、解除した側の値をすべてのエディタとレプリカに届けます。
- `value` の代入、`clear()`、置き換えを行う読み込みのような、ドキュメントを置き換える読み込みは、すべての `5.1.0` のエディタ、つまり読み込みを行ったエディタとそれを受け取る各エディタで、描画中のリレーションシップを終了させます。古いエディタは、その間も描画を有効なままにします。

セッション内のすべてのエディタと、そのドキュメントを保存する [replicationStore](./remote-storage.md#dispatch-dispatchsync) には、[同時編集](#concurrent-edits)が挙げる例外を除き、同時に行われた編集がどこでも同じ結果になるよう、`5.1.0` 以降を使います。論理名と辞書を保つのは、引き続き `4.2.0` 以降です。`1.2.0` より前の [MCP サーバー](../../mcp/live-and-headless.md#edits-made-at-the-same-moment)は、ここでは `5.1.0` より前のエディタとして扱われ、`5.1.0` より前のエディタは [Yjs](./yjs.md) ルームにはまったくバインドできません。

`5.1.1` からは、メモが[テーブルグループ](../../guide/guides/table-groups.md)に加わる、またはグループを離れる変更は、新しい種類のアクション `memo.changeGroup` で送られ、アクションをそのまま受け渡す中継であれば、新たに対応する必要はありません。このアクションが送られるのは、メモをグループの中や外にドロップしたとき、どのグループにも属さない表示しているメモの周りに新しいグループを描いたとき、テーブルと一緒にメモを選択して `Group selected tables` を実行したとき、選択にメモが含まれる状態で `Remove from group` を実行したとき、グループを削除したとき（そのグループの各メモについて）、コーディングエージェントが [MCP サーバー](../../mcp/tools.md#テーブルグループ)を通じてメモのグループを設定したとき、そしてそれぞれの Undo と Redo です。追加するグループがメモを持つ `Import and Add` や `setSchemaJSON` の追加もこれを送り、その Redo も同様ですが、その Undo はそれらのメモを削除するだけです。

`5.1.1` より前のエディタやレプリカは `memo.changeGroup` を無視し、パースですべてのメモの `groupId` を取り除くため、メモがグループに属している状態を目にすることはありません。ただし、`5.1.1` のエディタのグループのドラッグは、メモごとに `memo.moveTo` も送るため、そこでもグループのメモを動かします。そのエディタ自身の編集はメモのグループを何も知らないため、新しいエディタには次のような影響があります。

- そのエディタでグループの枠の中へドラッグしたメモはグループに加わらず、グループのメモを枠の外へドラッグした場合はグループに残り、枠が広がってそのメモを収めます。
- そのエディタでのグループのドラッグは、その `Auto Layout` と同じく、グループとそのテーブルを動かしますが、グループのメモはその場に残します。枠は広がって、そこに残った表示しているメモを収めます。
- そのエディタでの `Import and Add` は、追加するグループにメモを加えません。
- そのエディタが削除したグループは、各メモの `groupId` がそのグループを指したまま残ります。メモはどのグループにも属していないものとして扱われ、そのエディタで削除を Undo すると、メモはグループに戻ります。
- そのエディタでドキュメントの読み込み、ファイルの読み込み、`clear()` を Undo すると、すべてのエディタにそのエディタが持つドキュメントのコピーが読み込まれます。そのコピーでは、どのメモもグループに属していません。

そのようなエディタで保存したドキュメントではどのメモもグループに属しませんが、`4.0.0` 以降のものはテーブルのグループを保ちます。  
メモをテーブルグループの中に保つには、セッション内のすべてのエディタと、そのドキュメントを保存する [replicationStore](./remote-storage.md#dispatch-dispatchsync) に `5.1.1` 以降を使います。同時に行われた編集を調停するのは、引き続き `5.1.0` 以降です。同様に、`1.2.1` より前の [MCP サーバー](../../mcp/installation.md#アップデート)は、メモがどのテーブルグループに属しているかを認識も保持もしません。

## SharedStoreConfig

### getNickname

他のエディタで、このユーザーのマウスカーソルの横に表示するニックネームを設定します。  
ニックネームが未設定または空の場合、他のユーザーには `user` と表示されます。

```js
editor.getSharedStore({
  getNickname: () => 'nickname...',
});
```

### mouseTracker

このユーザーのマウスカーソルを他のエディタへ送信します。既定値は `true` です。  
他のユーザーから送られてきたカーソルは、ERD キャンバスに常に表示されます。

```js
editor.getSharedStore({ mouseTracker: false });
```

### focusTracker

このユーザーが作業している対象を他のエディタへ送信します。既定値は `true` です。  
フォーカスしているテーブルとセル、選択しているテーブル、メモ、テーブルグループ、キャンバス上でドラッグしているボックスが他のエディタへ送られ、そこに描画されます。  
ユーザーごとに固有の色が割り当てられるため、フォーカス中のテーブルの輪郭線、フォーカス中のセルの下線、選択中のテーブル、メモ、テーブルグループを囲む枠線、ドラッグボックスの破線の矩形で、それぞれを見分けられます。  
`4.2.0` からは、名前の表示のロックがオンの間や、読み取り専用のエディタが自分で表示を切り替えた後は、ユーザーごとに異なる[名前の表示](../../guide/guides/logical-names.md#collaborators)を見ていることがあります。自分の表示が描かないセルがフォーカスされている場合は、その代わりに描かれるセルに下線が引かれます。名前と論理名は互いの代わりになり、データ型とドメインも同様です。  
他のユーザーから届いた操作状況は、このオプションの設定にかかわらず常に自分のキャンバスに描画されます。  
Visualization タブの Flow モードでは、他のユーザーのフォーカスと選択はテーブルのカードに描画されますが、ドラッグボックスは描画されません。そこで選択したテーブルは引き続き送信されますが、そこでドラッグしたボックスは送信されません。

```js
editor.getSharedStore({ focusTracker: false });
```

両方のトラッカーを無効にすると、自身の操作状況を一切送信しない単純な中継として shared store を使えます。  
他のエディタから送られてくる操作状況は、引き続き受信して描画します。  
VS Code、Obsidian、JetBrains IDE、Google Drive のエディタはこの方式で動作しています。

```js
editor.getSharedStore({ mouseTracker: false, focusTracker: false });
```

マウスカーソル、フォーカス、選択、ドラッグボックスは、ドキュメントの変更と同じストリームを流れますが、一時的なものです。  
これらはドキュメント、Undo の履歴、`editor.value` のいずれにも入らないため、トランスポートが破棄しても構わず、replicationStore も無視します。

## SharedStore

### connection, disconnect

現在の接続状態を設定するメソッドです。  
切断されている間は、変更を内部のバッファに保存します。  
再び送信可能な状態になると、バッファに溜まった変更を購読者へ発行します。  
既定の状態は接続済み（`connection`）です。

```js
sharedStore.connection();
sharedStore.disconnect();
```

### dispatch, dispatchSync

他のエディタインスタンスの変更を、現在のエディタインスタンスに反映します。  
バッチに他のエディタからのレジスタの要求が含まれている場合（参加者の最初の [subscribe](#subscribe) が送るものなど）、store は、レジスタを保持していなければ応答せず、保持していれば、そのレジスタとバージョンを購読者を通して応答します。  
`5.1.0` からは、応答の前に、[flushStreamBuffers](#flushstreambuffers) と同じように、保留しているすべてのストリームのバッチを先に送信します。これは、応答が伴う各バージョンが、他のエディタにすでに送信された書き込みに基づくようにするためです。そのため、参加者が到着すると、セッション内のすべてのエディタが、保留しているドラッグ、パン、拡大・縮小、色の変更、メモのサイズ変更を同時に送信します。

```js
sharedStore.dispatch(actions); // async
sharedStore.dispatchSync(actions); // sync
```

### subscribe

エディタの変更を購読します。  
購読者が 1 つも存在しない間はエディタから何も送信されず、それまでの変更はバッファに保存されます。  
最初の subscribe では、[同時に行われた編集](#concurrent-edits)を調停する共同編集用のレジスタも他のエディタに要求するため、後から参加したエディタも同じように編集を調停します。  
ドキュメントは届かないため、後から参加するエディタには先に[初期値を設定](#参加者への初期値の設定)します。`5.1.0` からは、その初期値にレジスタを含めることもできます。  
`4.0.0` からは、最初の subscribe の後に `setInitialValue`、または `5.1.0` からは [reseed](#reseed) がそのエディタにドキュメントを読み込むたびに、store は改めて要求します。

```js
const unsubscribe = sharedStore.subscribe(actions => {
  // send...
});
```

### flushStreamBuffers

この store がまだ送信せずに保持しているストリームのバッチを、変更が途切れるのを待たずに今すぐ送信します。  
`3.9.2` からは `getSharedStore` が返す store で動作します。`3.9.1` では型にメソッドはありますが、何もしません。  
テーブル、メモ、テーブルグループの移動、色の変更、メモのサイズ変更、ビューのスクロールや拡大・縮小は、それぞれ小さな変更のストリームとして行われます。テーブルグループのサイズ変更はそうではなく、ドラッグを終えたときに 1 回だけ送信されます。  
store は各ストリームを 1 つのバッチにまとめ、ストリームの変更が 200ms 途切れるまで、2 段階で保持します。色の変更とメモのサイズ変更は両方の段階を通るため、`5.1.0` より前のすべてのストリームと同じく、最後の変更から約 400ms 後に送信されます。`5.1.0` からは、ドラッグ、パン、拡大・縮小は最初の段階の後、つまり最後のステップから約 200ms 後に、行き着いた先として送信されます（[同時編集](#concurrent-edits)を参照）。  
呼び出すと、両方の段階でその待機が終わります。store が接続済みの状態であれば、購読者は呼び出しが戻る前にバッチを受け取ります。保持しているものがない場合は、呼び出しても何も送信されません。  
store 自身の `destroy` もエディタの `destroy` も、まだ保持しているバッチを破棄します。そのため、タブを閉じるときのように、store を手放しても他のエディタに最後の変更を残したい場合は、先にこれを呼び出します。

```js
sharedStore.flushStreamBuffers();
sharedStore.destroy();
```

### getLWW {#getlww}

`5.1.0` からは、エディタの共同編集用のレジスタ（[同時編集](#concurrent-edits)を参照）のコピーを返します。  
コピーは JSON を通して作られるため、`JSON.stringify` にそのまま渡せる単純なオブジェクトであり、それを変更しても store のレジスタは変わりません。  
これはそのまま、別の store の [mergeLWW](#mergelww) または [reseed](#reseed) に渡します。その形はエディタ固有のものなので、フィールドを読み取らないでください。  
[参加者に初期値を設定する](#参加者への初期値の設定)ときは、[getVersion](#getversion) およびエディタの `runtimeValue` と同時に読み取ります。

```js
const lww = sharedStore.getLWW();
```

### mergeLWW {#mergelww}

`5.1.0` からは、別の store が [getLWW](#getlww) で渡したレジスタをこの store のレジスタに取り込み、それぞれについて大きいほうのバージョンを保持します。また `version` をエディタのクロックに取り込み、クロックは自身のバージョンと渡されたバージョンの大きいほうを保持します。  
ドキュメントは何も変更しません。`value` も `runtimeValue` も 1 バイトも変わらず、Undo のエントリーも `change` イベントもありません。後の書き込みが上回らなければならないバージョンを引き上げるだけなので、その後は、渡されたレジスタより古い書き込みは拒否され、エディタの次の編集は `version` を超えるバージョンを伴います。  
何も送信せず、何にも応答しません。参加者の最初の subscribe が他のエディタの応答から受け取るものを、直接取り込む手段です。  
必ず `setInitialValue` の後に呼び出してください。`setInitialValue` と [reseed](#reseed) は、呼ばれるたびに保持しているレジスタを破棄し、その前に行った `mergeLWW` が取り込んだものも失われるためです。

```js
sharedStore.mergeLWW(lww, version);
```

### getVersion {#getversion}

`5.1.0` からは、エディタのクロックが取り込んだ最も高いバージョンを返します。これは、エディタが行った、または取り込んだ変更のバージョン、参加時にやり取りされるレジスタの要求と応答のバージョン、`mergeLWW` または `reseed` に渡された各 `version` のうち、最大のものです。  
カーソル、フォーカス、選択、ドラッグボックスは、自身のものでも他のエディタのものでも、これを動かしません。  
同時に読み取った [getLWW()](#getlww) と一緒に、参加者の [mergeLWW](#mergelww) または [reseed](#reseed) に渡します。これは、そのアクションが伴うものと同じ[バージョン](#concurrent-edits)です。

```js
const version = sharedStore.getVersion();
```

### forgetPeer {#forgetpeer}

`5.1.0` からは、指定した ID のエディタが送ったカーソル、フォーカス、選択、ドラッグボックスと、それぞれが待っていた有効期限を、ただちに削除します。他のエディタのものはそのまま残ります。  
ID は、そのエディタの shared store が送るすべてのアクションが伴う `meta.editorId` です。このエディタが何も保持していない ID を渡しても、何も変わりません。  
トランスポートがピアの退出を検知したときに呼び出します。呼び出さない場合、ピアが送ったものは期限が切れるまで描画されたままになります。カーソルは最後に受信してから 30 秒後、フォーカスと選択は 90 秒後、ドラッグボックスは 3 秒後です。

```js
sharedStore.forgetPeer(editorId);
```

### reseed {#reseed}

`5.1.0` からは、再参加のときのように、セッションのドキュメントをエディタで開き直します。[Yjs](./yjs.md) のバインディングは、初期値が設定されたルームにバインドするときにルームのドキュメントを開くためにこれを呼び出し、再参加のたびにも呼び出します。ルームに参加済みであれば、画面は保たれます。  
[setInitialValue](../erd-editor-element.md#setinitialvalue) と同じように `value` を読み込み、[mergeLWW](#mergelww) と同じように `lww` と `version` を取り込むため、store はその後、渡されたレジスタとまったく同じものを保持し、クロックは自身のバージョンと `version` の大きいほうを保持します。また、Undo の履歴を空にし、`setInitialValue` とは異なり、選択とフォーカスを破棄します。これらは、その値がもう保持していないものを指している可能性があるためです。  
後述する論理名からの生成を除き、Undo のエントリーを作らず、`change` イベントを発行せず、変更も送信しません。store に購読者がいたことがあれば、そのような読み込みのたびに送られるレジスタの要求を送信します。レジスタをすでに渡したトランスポートは、この要求を破棄してもかまいません。[focusTracker](#focustracker) がオンであれば、解除された選択とフォーカスも送信します。  
`setInitialValue` と同じように、[readonly](../erd-editor-element.md#readonly) が設定されている間も動作し、Flow のビューを破棄し、描画中のリレーションシップを終了し、メモ、テーブルグループ名、セルのエディタを閉じて、入力中だった内容も同じように保持または破棄します。論理名のセルを閉じるときに閲覧者が入力した内容から生成される名前は、通常の編集として扱われます。つまり送信され、Undo でき、`change` イベントとして発行されます。

`keepScreen` を指定しない場合、画面は `setInitialValue` の後と同じように、値が保持している内容を表示します。`keepScreen: true` を指定すると、閲覧者の画面のうち次のものが、その画面でだけ、読み込まれたドキュメントの上に元どおり重ねられます。

- スクロール位置と拡大・縮小のレベル。ただし、要素がそれらを表示した後に限ります。一度も表示されていない場合や、非表示のまま読み込まれてそれ以降表示されていない場合は、後から参加するエディタと同じように、値が指定する位置で開きます。
- タブ。読み込みがタブを移動させた場合に限ります。設定タブでは、そこでオンにした `Canvas Type` のロックが指す、閲覧者が来たタブも含みます。
- 閲覧者が自身のロックの下で自分で表示した名前の表示と各 Code Generator の設定。ただし、読み込みの前にそのロックがオンで、読み込みの後もオンのままであり、同じロックした値を保持している場合に限ります。そのため、その間にピアがある設定のロックを解除し、別の値に変更して再びロックした場合、エディタは新しいロックした値で開きます。読み込みの前または後にロックがオフであれば、読み込まれた値が表示されます。
- 読み取り専用の閲覧者が自身の画面で変更したすべての設定。ロックの状態にかかわらず保たれます。

これらは何も送信されず、`value` と `runtimeValue` は引き続き読み込まれたドキュメントを返します。ピアが後からロックを解除すると、この方法で保たれたコード設定は、他のロックの解除と同じように置き換えられます。  
エディタが編集できる状態で行った閲覧者の次のスクロールまたは拡大・縮小は、保たれていたスクロール位置と拡大・縮小のレベルを再びドキュメントのものにし、画面の現在位置を先頭にして送信されるため、レプリカもその拡大・縮小を受け取ります。

再度の初期値設定は、store が保留しているものをそのまま残します。保留しているドラッグ、パン、拡大・縮小は、その後に、初期値を設定し直したドキュメントから読み取って送信されます。色の変更とメモのサイズ変更は、エディタにはもう表示されていなくても、行われたとおりに送信されます。`disconnect()` が保留していたものは、`connection()` で送信されます。  
そのため、先に [flushStreamBuffers](#flushstreambuffers) を呼び出し、それが発行したものを送信してから、それを含む値で初期値を設定し直します。切断されている間は、初期値を設定し直さないでください。

```js
sharedStore.reseed(seed.value, {
  lww: seed.lww,
  version: seed.version,
  keepScreen: true,
});
```

### destroy

sharedStore のインスタンスを完全に破棄します。  
エディタ自体はそのまま残るため、セッションから抜けてもドキュメントの編集を続けられます。  
エディタが返した最後の sharedStore が破棄されると、マウスとフォーカスのトラッカーは停止します。  
store がまだ保持しているストリームのバッチも一緒に破棄されます。送信するには、先に [flushStreamBuffers](#flushstreambuffers) を呼び出します。  
他のエディタが送ったカーソル、フォーカス、選択、ドラッグボックスは、期限が切れるまで描画されたままになります。`5.1.0` からは、[forgetPeer](#forgetpeer) で 1 つのエディタのものをただちに削除できます。

```js
sharedStore.destroy();
```
